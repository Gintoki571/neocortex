# DOX framework

- DOX is highly performant AGENTS.md hierarchy installed here
- Agent must follow DOX instructions across any edits

## Core Contract

- AGENTS.md files are binding work contracts for their subtrees
- Work products, source materials, instructions, records, assets, and durable docs must stay understandable from the nearest applicable AGENTS.md plus every parent AGENTS.md above it

## Read Before Editing

1. Read the root AGENTS.md
2. Identify every file or folder you expect to touch
3. Walk from the repository root to each target path
4. Read every AGENTS.md found along each route
5. If a parent AGENTS.md lists a child AGENTS.md whose scope contains the path, read that child and continue from there
6. Use the nearest AGENTS.md as the local contract and parent docs for repo-wide rules
7. If docs conflict, the closer doc controls local work details, but no child doc may weaken DOX

Do not rely on memory. Re-read the applicable DOX chain in the current session before editing.

## Update After Editing

Every meaningful change requires a DOX pass before the task is done.

Update the closest owning AGENTS.md when a change affects:

- purpose, scope, ownership, or responsibilities
- durable structure, contracts, workflows, or operating rules
- required inputs, outputs, permissions, constraints, side effects, or artifacts
- user preferences about behavior, communication, process, organization, or quality
- AGENTS.md creation, deletion, move, rename, or index contents

Update parent docs when parent-level structure, ownership, workflow, or child index changes. Update child docs when parent changes alter local rules. Remove stale or contradictory text immediately. Small edits that do not change behavior or contracts may leave docs unchanged, but the DOX pass still must happen.

## Hierarchy

- Root AGENTS.md is the DOX rail: project-wide instructions, global preferences, durable workflow rules, and the top-level Child DOX Index
- Child AGENTS.md files own domain-specific instructions and their own Child DOX Index
- Each parent explains what its direct children cover and what stays owned by the parent
- The closer a doc is to the work, the more specific and practical it must be

## Child Doc Shape

- Create a child AGENTS.md when a folder becomes a durable boundary with its own purpose, rules, responsibilities, workflow, materials, or quality standards
- Work Guidance must reflect the current standards of the project or user instructions; if there are no specific standards or instructions yet, leave it empty
- Verification must reflect an existing check; if no verification framework exists yet, leave it empty and update it when one exists

Default section order:
- Purpose
- Ownership
- Local Contracts
- Work Guidance
- Verification
- Child DOX Index

## Style

- Keep docs concise, current, and operational
- Document stable contracts, not diary entries
- Put broad rules in parent docs and concrete details in child docs
- Prefer direct bullets with explicit names
- Do not duplicate rules across many files unless each scope needs a local version
- Delete stale notes instead of explaining history
- Trim obvious statements, repeated rules, misplaced detail, and warnings for risks that no longer exist

## Closeout

1. Re-check changed paths against the DOX chain
2. Update nearest owning docs and any affected parents or children
3. Refresh every affected Child DOX Index
4. Remove stale or contradictory text
5. Run existing verification when relevant
6. Report any docs intentionally left unchanged and why

## User Preferences

When the user requests a durable behavior change, record it here or in the relevant child AGENTS.md

# neocortex AGENTS.md

## Purpose

Long-term memory for AI agents, v0.1.4. Rust, one crate, one binary `neocortex` (CLI + MCP stdio server). One SQLite file holds memories (FTS5 BM25 + sqlite-vec), an entity/relation knowledge graph (graphqlite projection) and bi-temporal facts. Embeddings: UltraBERT-Embed-150M on candle (pure Rust, CPU). No LLM inside, no Python at runtime (offline tooling only, in `scripts/` and `eval/extract/reference/`), no network.

Target hardware (binding, user requirement 2026-10-26): neocortex must run well in low-resource environments: old CPUs (few cores, no recent SIMD extensions assumed) with 2-3 GB of total RAM, such as cheap VPSes and old laptops; the agent and the OS share that RAM. Every change is judged on accuracy AND footprint: peak RSS, cold start, recall/remember latency on 1-2 cores, model and DB size on disk. Builds for other platforms (ARM, Android) are out of scope for now. Working budget: peak RSS well under 512 MiB during cold recall and remember; f32 cannot meet it (615 MiB), q8 does (see Verification). Footprint numbers live in Verification and `docs/research/footprint.md`.

Design (binding): `docs/superpowers/specs/2026-10-22-neocortex-design.md`. Plan: `docs/superpowers/plans/2026-10-23-neocortex-plan.md`. Pre-rewrite ReMem code: git tag `remem-final`.

## Local Contracts

- Version stays `0.1.4` until the user says otherwise.
- Tests that create temp files or directories use `tests/common/mod.rs` `TempDir` (std only; removed on drop, also on panic). Never leave a `neocortex-*` path under the system temp dir without a guard. `src/import.rs` unit tests share it via `#[path]`.
- Dependencies: rusqlite (bundled), sqlite-vec `=0.1.9` (0.1.10-alpha does not compile), graphqlite `0.12`, candle-core/candle-nn `0.11`, tokenizers (`fancy-regex`, no default features), serde, serde_json. Adding any other crate needs a one-line reason here.
- Relational tables are the source of truth; graphqlite nodes/edges are a projection rebuilt by `neocortex reindex`.
- Vector storage mode (`db::VecMode`): the four vec0 tables (`memories_vec`, `entities_vec`, `predicates_vec`, `relations_vec`) are `float[768]` (f32) or `int8[768]` (int8: each vector scaled so its largest element is 127; cosine is scale-invariant, and `decode` renormalises to unit length). New databases take `NEOCORTEX_VEC` (default f32); the mode is `schema_meta.vec_mode`, kept on every open. Every vec0 bind goes through `db.vec_sql("?n")` (int8 needs sqlite-vec's subtype), every blob write through `db.vec_blob`, every read-back through `db.blob_to_vec` (dequantises); cosine math stays f32. `neocortex migrate-vectors --to int8` rewrites in one transaction, then VACUUM (f32 is the only source). Default stays f32: on 8af053c + lane, int8 holds fixtures (0.953/0.895), multihop (0.825), multihop2 (0.830) and world-300 (0.992 acc@10) but holdout MRR is 0.792 against the 0.793 floor (f32 0.794). world-300 DB 21.3 MB -> 8.9 MB.
- Memory KNN prefilter (`Config.vec_prefilter`, default `off`; `bit` via `eval --set vec_prefilter=bit` or `NEOCORTEX_VEC_PREFILTER=bit` at open): `memories_bits` is a vec0 table of one sign bit per dimension (`bit[768]`, 96 B of bits, 128 B/memory with rowids and the `live` column) derived from `memories_vec` by `db::sign_bits` (LSB-first, sign of each component). `recall`'s memory KNN takes the top `vec_prefilter_n` x k rows (k = the KNN request, at least `SEM_FACTS` 100) by Hamming distance and reranks them with the exact stored vectors; `vec_prefilter_n` defaults to 10. `db::bits_knn` reads the vec0 chunk shadow tables directly (one popcount pass, O(rows); the module's own KNN is O(rows x k) in its top-k selection and costs as much as the exact scan at k=1000) and falls back to that KNN if the pinned sqlite-vec 0.1.9 layout is missing. `db::ensure_bits` creates and backfills the table (`meta.vec_bits` marks completion, so a killed backfill resumes). The first call on a connection reconciles it with `memories_vec` (row count and max rowid; a mismatch backfills the missing rows and deletes orphan bit rows). The reconcile catches rows added or removed by an older binary while no knob-on connection was open. It does not catch a live-flag change or id reuse (memory ids are reused after a hard forget of the max id) made by an older binary while a knob-on connection is open. Later calls on that connection only probe that the table exists, so a recall costs one catalog read. The reconcile waits at most 50 ms for a writer (`BITS_BUSY`) and then errors: the recall takes the exact scan and the next recall retries. `db::has_bits` is probed on every write (no per-connection cache), so a knob-off connection writes bits once another process creates the table, and a dropped table skips bit writes instead of failing them; every vector write goes through `db::insert_memory_vec` / `db::set_memory_vec_live` / `db::delete_memory_vec` so it stays in sync, knob off never creates the table and takes the exact scan unchanged, and a read-only database without it falls back to the exact scan.
- One connection per process (`db::Db`, prepared-statement cache 64): sqlite-vec via `sqlite3_auto_extension`, graphqlite via `Connection::from_rusqlite`. Writes go through `Db::write` (BEGIN IMMEDIATE). Cypher runs inside the same transaction.
- An open is read-only in steady state (OPS-FLAKE, 2026-11-06): `ensure_additive_tables` probes `sqlite_master` through `table_exists`/`index_exists` and runs only the DDL that is missing, because SQLite takes the write lock for a no-op `CREATE INDEX IF NOT EXISTS`; and the bundled graphqlite extension is loaded with `LOAD_BUSY` (100 ms) once its `nodes` table exists, because its init replays the same write-locking DDL on every load (a busy writer stalled each open for two 5 s busy timeouts). A fresh file keeps `OPEN_BUSY` (graph tables still to create); an uncontended open repairs anything a skipped DDL left behind. Migrations, the name-token backfill and the seed reconcile still write, once, when their input is missing.
- A write transaction waits `WRITE_BUSY` (30 s), not the 5 s open budget (OPS-FLAKE, 2026-11-06): a writer only ever queues behind another writer's milliseconds-long transaction, but the host can stall that holder (another process's IO storm made the 8-writer tests fail with "database is locked" even after the open fix; under pure CPU load at load avg 90 they pass). `Db::write_within(budget, ..)` takes the budget, and the best-effort access-history write a recall makes passes `OPEN_BUSY` (as does the bit-table reconcile, `BITS_BUSY`) so a read never pays the patient wait.
- Validity is half-open `[valid_from, valid_to)`; system retirement is `expired_at`. Times are unix seconds UTC.
- One live memory per `content_hash` (unique partial index); a hash hit only counts as a duplicate when kind + folded text match. A memory is evidence for a current relation only while it is itself current (neither retired nor ended — the same live-evidence definition `validate` uses for "current but every memory that states it has ended"); ending the last live evidence memory ends the relation at the latest evidence `valid_to` (`relations_losing_their_last_evidence` hold: an already-ended relation keeps its history while any non-retired memory states it, so forgetting one witness of a historical fact does not erase it). A memory's end (`--until`, `invalidate m`, supersede) ends the relations it alone still evidenced; soft forget retracts them (`expired_at`, no end date); hard forget and merge patch the graph projection incrementally, never `rebuild_all`.

Places are not evidence (a city is a hub), nor are tools, untyped entities, a bare-name card cosine, memory context or descriptions (generic role descriptions agree across people; a description-less card embeds as the bare name). - Renames join old and new names only when the caller asserts them (H3-10, fix-round-4 contract: TEXT cue never merges): prose declarations ("X was renamed to Y", "X is now Y", "X is now called Y", "X changed her name to Y", "Y (formerly X)", "Y (now Z)", "Y (renamed from X)") are parsed by `remember::rename_pairs_text` and filtered by every pre-round-3 guard — hedged ("might rename", `rename_blocked` over `HEDGES` plus will/going/intend before the cue and in the same clause after it, stopping at ","/";"/" and "/" but "), negated, questioned ("Was X renamed?"), reverted ("then back to X"), passive ("called by the team", cue must end before the new name), generic (written-form all-lowercase except sentence-initial/hyphen-joined, determiner-following capitalised word written lowercase elsewhere, plus the word-list/file-name safety net), bare-first-name/shared-first-name, both-live undated, bare `is now` same-type, different-type and ambiguous-norm (either norm names >1 entity) — and a passing pair becomes a `renamed?` hint naming both entities with `e<id>`s and the exact confirm call (`entities:[{name:new,same_as:e<old>}]` or `relations:[{source:old,predicate:"renamed to",target:new}]`), storing nothing (no merge, no fact). A caller-asserted rename — a relation whose predicate is exactly `renamed to` (old-first, source=old/target=new) or `renamed from` (new-first, source=new/target=old), or `same_as` `{name:new,same_as:old}` when both rows already exist — merges via `engine::merge_entities_in` (which also moves `relations.subj`) so facts move to the survivor, the old name survives as an alias, and a "new formerly called old" holder fact (no alias row, lookups land on the survivor) is written at `valid_from`; only different-type (skip+hint) and ambiguous-norm (candidates) apply, and a both-live undated structured merge still happens and reports its ended facts. Every other spelling (`formerly called`, `previously called`, `now called`, `now known as`, `renamed`, `rename to`, `formerly`, `previously`) is a plain relation and never merges ("Ana previously called Bo" is a phone call), byte-identical in storage to main. No other candidate may sit between old and new (two renames emit two pairs, not a chain). Rename handling runs after relation writes in `write_prepared`; duplicate writes are skipped. Forgetting the confirming memory retracts the formerly-called fact but never un-merges; forgetting a text-hint memory does nothing.

- Asked-predicate channel (H2-14): the fact channels render live rows canonically, so a question phrased from the inverse side ("who does Mira report to", "who is Mira's manager", "who is Mira accountable to") used to return no fact when the only row was "Noah manages Mira". `recall::asked_family_facts` now reads the asked family from the question and runs after the other fact channels, before ordering/duration: `asked_relation` takes a role noun first (`ROLE_SURFACES`: manager/boss/supervisor -> `manage`, mentor -> `mentor`, mentee -> `mentor` from the other side), then a 1-4-word `text::norm_predicate` window through `predicate_aliases` restricted to `p.seeded=1` and `ASKED_GROUPS` (`manage`, `mentor`, `work at`), with `active` = the phrase's subject is the canonical src (`p.inverse_of` absent or higher id). Direction: a role noun uses the auxiliary before the mention (`do/does/did` -> side `Src` iff the role is the canonical src), a verb uses `(active, before)`; the row is rendered from the named side only when that mention precedes the phrase and is the row's non-canonical end (`viewer_before`), so "who manages Mira" stays "Noah manages Mira". Results replace the same-id fact in place (keeping `current_values`/`ended`) or prepend, truncated to 8, and are skipped for negation questions. Cost: `has_asked_cue` returns before any SQL for a question with no role or family word, and the 1-4-word windows share one `prepare_cached` `alias_norm IN (...)` lookup, because the per-window SQL cost +10.8% p50 on world-300; with both, p50 is 107-109 ms against base 107-156 ms on the same DB (2026-10-29). Read-side only: the role nouns are deliberately not write aliases (a bare role noun is direction-ambiguous for writes), so `employs`/`works at` role nouns stay out. `mentor`/`mentored by` are seeded as a pair (see `src/db.rs`), so a canonical mentor write renders "mentored by" for the mentee.
- `recall` adds a query-directed path channel (`paths::search`, beam 24, depth 3, `PATH_WEIGHT` 2.5) plus a semantic multi-hop channel (`paths::search_semantic`: relation KNN k=100, residual-question hop scoring, >= 2-hop chains, weight `w_sempath` 0.25) and renders the path facts (the best lexical and the best semantic chain both reach the facts); the lexical beam is skipped on history-intent questions and both beams on negation questions (a negation that scopes the speaker's memory verb - "don't/can't/cannot remember|recall|recollect" - is not a negation question, `paths::negation_intent`). Exclusion questions (`paths::exclusion_intent`: a wh-word + noun + its negated predicate, a negated relative clause, `except`/`excluding`/`other than`/`apart from`) are not negation questions either: the ordinary channels run, and a query-time `excl` channel (`EXCLUSION_WEIGHT` 2.5) ranks the memories of typed entities that lack the asked property (`paths::exclusion_entities` resolves the noun through `entities.type` and the property through `entity_aliases`), the memories of the entities that have it are demoted (`EXCLUSION_PENALTY` 0.5) and their facts sort last; when the noun type or the property names nothing stored the channel is empty and the query is answered exactly as before (a type with more than `EXCLUSION_MAX_ENTITIES` 1000 members is skipped the same way, and the seeds are ranked in bounded chunks so a whole type's vectors never sit in RAM). Up to three chains are rendered (`paths::top_chains`: best lexical, best semantic, next lexical; `facts` limit 8). Opt-in (`Config.prose_margin`, default infinity = off; `eval --set prose_margin=0`): when the best semantic chain uses prose (relation-less) memories and beats the best chain with another terminal by that margin, up to two of those memories are rendered first in `facts` as `[m<id>] <bridge entity> · <text>` (`FactHit.memory`; `paths::prose_facts`). Measured: off, Q1 + `top_chains` give mh2 +2; margin 0 adds +1 more on mh2 but no gain on a private blind set and +1.5% to +4.5% context tokens, so it stays off. An empty recall is returned when no lexical, entity, relation or path support exists and the best cosine is below `ABSTAIN_COSINE` (0.18).
- Correction hints (H3-04/H3-05, `src/correction.rs`; knob `correction_hints`, default off; `eval --set correction_hints=on` or `NEOCORTEX_CORRECTION_HINTS=1` at open). With the knob on, `remember` returns `possible_supersedes` (older live memories the new text may correct) and `recall` marks the old hit `[maybe superseded by m<id>]`. Rule (`is_correction`): an explicit cue (correction, actually, not X but Y, changed from, instead of, no longer); a numeric value of the old text restated in the new text together with a value the old lacks; shared subject words (>= 2 and >= 40% of the smaller set). Years, ids and build/version numbers are not values. Candidates are live, not relation-backed and not later-dated. Nothing is ended; the caller decides (`forget`, `invalidate` or `supersedes`). Designed misses: corrections with no number ("Ines, not Dima") or no cue ("moved to"). Fixture: `tests/fixtures/correction_pairs.json` (`cargo test correction` prints precision/recall).
- `recall` also reports unfinished hops in `next: Vec<NextHop>` (`{entity, name, want, why}`, at most two, omitted when empty; `entity` + `want` feed `follow`). A hint appears when the best chain's last hop does not match the question's wh-frame, or when no chain covers the asked relation; it is suppressed when the frame already matches the returned facts/memories (lexical cue guard before the frame embedding, then cosine >= `hint_tau`). `hint_tau` defaults to 0.40 and `0` disables hints; hints never change ranking or the scored context, and average well under 30 extra output tokens per recall.
- Two optional channels are measured experiments and default to 0: `tlink` (`w_tlink`; temporal links are always written between memories within `tlink_window_hours` that share an entity, weight `max(0.3, 1-gap/24h)`, at most `tlink_cap` per endpoint) and `causal` (`w_causal`; only on why-intent questions, over the seeded `cause` group; `causal_extract` optionally adds one conservative in-memory text-cue relation when the agent supplied none).
- Access is recorded for every memory `recall` returns, in one `Db::write` transaction (`access_count`/`last_access` totals plus `memory_access` timestamps, capped by `access_keep`; `0` keeps no history). `w_retention` (default 0.05: neutral on fixtures/world/multihop-holdout2, +0.007 MRR on holdout) blends `rank::retention` into ranking; `stats.cold_memories` is a report-only hint (retention < 0.15).
- Communities are deterministic Leiden (`graph::leiden`, seed 7, resolution 1.0) over the live weighted snapshot (memories, entities, mentions, live relations, similar). The community graph weights a mention edge by `1/sqrt(deg(memory)*deg(entity))` (`kg::build_snapshot(.., selective_mentions)`, community detection only: the PPR snapshot keeps the flat 1.0, so ranking is untouched), because a hub's 53 mentions otherwise out-weigh its 8 relations and modularity isolates it; then `kg::attach_singletons` moves an entity that is alone in its community into the community holding most of its live relations (ties: more evidence, then the lowest id). Ids are remapped to the previous run by greedy member overlap, so `[cN]` stays put while the graph only grows. `overview` and the `entity` card read the table; recall scoring does not, so communities never move retrieval scores. Modularity is measured on the entity-induced subgraph (`kg::entity_subgraph`) with the partition the engine serves (`kg::community_quality`, printed by `examples/community_eval`): memory nodes only pull a hub into a community, they say nothing about how entities group, and scoring Leiden on the flat snapshot (the old probe) cannot see the change. Measured 2026-10-30 on world-300: served Q 0.4525 vs the flat partition's 0.3170, 25 communities, 0 singleton entity communities; project scenario Q 0.4463 -> 0.5550; `tests/communities.rs` keeps determinism, id stability, the hub case and the served-partition measurement.

- `Config.anchor_tiers` (default empty = exact aliases only; `eval --set anchor_tiers=1b`) adds query-anchor tiers in `src/anchor.rs`: `w` demotes generic or shared aliases (one word not in the entity's own name, or an alias naming several entities) to weak anchors, `1` makes a capitalised non-initial query word that is the first/last word of exactly one multi-word entity name a weak anchor, `2` resolves a role noun next to an anchor through its one live relation; weak anchors seed PPR and start both beams, and only `b` (block pass-through) / `x` (enable prose hops) / `p` (both) give them the strong-anchor side effects. Kept off: every config tested on multihop-holdout2 (`w`, `w1`, `w1b`) scored 0.820 vs main 0.830 on the same DB; `1b` (fixtures/holdout unchanged, multihop-holdout 0.825 -> 0.8875) was not run on it (2026-10-26, lane nc-anchor).
- Text-only retraction (TM-10, H3-12): every non-duplicate write whose text carries a `RETRACTIONS` cue is matched against live relations of that group, including writes that supply their own relations (the ids just written are excluded, so prose never retracts its own assertion). When a generic cue ("no longer", "is/was no longer") carries a verb phrase before the object ("no longer reviews", "no longer approves"), it ends a live fact only when that verb matches the fact's predicate (`remember::verb_matches_relation`: same canonical, same ontology group through `predicates`/`predicate_aliases`, the same verb lemma with the same preposition tail, or a `RETRACTION_VERB_SYNONYMS` pair - head/lead, run/manage, oversee/supervise - for a synonym the ontology cannot alias because the word is also a role noun; "approves" does not end "reviews", "works with" does not end "works at"). An `-ly` adverb before the verb is stripped from the phrase ("no longer actively reviews" -> "reviews"; `remember::verb_phrase`) and does not consume the object lookahead; generic cues without a verb ("is no longer at") keep matching any predicate; the cue→object lookahead spans up to four non-adverb words so "verb + noun + prep + target" is found ("no longer supplies parts to Globex"); and "no longer only" / "no longer just" / "not only" scopes exclusivity rather than retraction and ends nothing - the scope word counts only between the cue and the object or immediately before the cue, never after the object ("no longer works at Acme, only at Brightline" still ends the fact; the trailing clause states the new state). `there` as a pronoun-like object (`THERE` sentinel, `remember::there_places`) resolves to the subject's single live place for the matching group/verb ("no longer works there" / "works remotely there" with exactly one live work-at value ends it); two or more live places return conflict candidates and end nothing, zero live places end nothing, and a scope tail after `there` ("on Fridays", `object_tail` Noun) ends nothing. The bare "stopped" cue (`VERB_REQUIRED_CUES`) is a retraction only when the gap names a verb, so "stopped working at Acme" ends "works at" and "stopped reviewing" ends "reviews" while "stopped by Acme" ends nothing, and any negating word directly before the cue ("never stopped ...", "has not stopped ...", "hasn't stopped ...", in every apostrophe spelling; `remember::negating_word`) stays positive. Names come from the memory entities, heuristic candidates, alias n-grams and resolved first names: a first name belonging to one stored person (or to the supplied one when several share it) stands for the full card ("Maria divorced Tom"), and two or more candidates make the mention ambiguous (reported, never ended). The sentence ends the single match at `valid_from` (reported in `invalidated`); several matches return `conflicts` and end nothing. A coordinated pair before the cue ("A and B are no longer partners") is one retraction of the pair relation: `PAIR_NOUNS` maps the noun to a group and the generic group is narrowed by the noun in the fact. A live row recorded at ingest time matches even when the text dates the retraction earlier ("divorced ... in 2024"): a recorded start at or after that date is system-retired (`valid_to` = start, `expired_at`), while an already-ended row must contain the date. The name must be the whole object of the cue: a possessive, a ditransitive object or a following noun rejects it, and only a clause boundary, a time expression ("as of ...", "since/until/from/after <date>", "on/in <ISO date or YYYY-MM>") or an employment tail ("to join", "for <Entity>") may follow; the determiner immediately before the name belongs to the object phrase ("the core team"), an earlier one rejects the match; the object matches a stored relation endpoint by entity norm, so a different object ("payment code" vs "payment-adjacent code") ends nothing; the employment pattern includes "left his/her/their job|position at X". A hedge or report in the clause (`almost`, `might`, `thinks`, `said that`, ...) returns the match as `conflicts` and ends nothing. Plans (`will`, `going to`, `plan to`, `next <unit>`, `in N <unit>`) resolve a future `valid_from` via `temporal::future_window` or get the tag `planned`; `recall` drops `planned`/future rows unless the query asks for plans, takes a window that starts in the future, or has future-event intent (`temporal::future_event_intent`: "when does X start", deprecation/shutdown/freeze/launch cues) and the row shares at least two query tokens (`recall::planned_matches_query`). Recurrence cues tag `recurring` and keep the rule text. Ordering intent sorts memories and facts by `valid_from` (a `who <past predicate> ... before <non-time word>` question is a predecessor frame, not ordering — `temporal::predecessor_frame`, only when the subject is unknown and the verb is one of the `past_state_intent` predicates, so "who did Tessa lead before Emil" and "which project did Tessa lead before Aspen refresh" stay ordering; a time value after `before` still is), except that a predecessor hit — an ended candidate the question anchors to the successor via a shared predicate and endpoint — keeps relevance order with the 4x ended boost, because the answer is the holder whose relation ended when the successor's began, not the oldest memory (H3-13b); duration intent fills `duration` from the stored `[valid_from, valid_to)` interval (calendar units, "ongoing since …") and keeps relevance order, because sorting by date put unrelated older rows above the answer.
- Status yes/no (H3-11): a question that starts with an auxiliary (is/are/was/does/has...) and carries `still`/`anymore`/`currently` and names both ends of an ended relation (`recall::ended_pair_facts`) adds that relation to the facts block, marked ended with its end date. Live rows never come from this path; other questions are unchanged.
- Negated-value questions (H2-03): a verb-phrase negation asking for the excluded or ended value ("what database does Lumen not use", "what does Ana no longer work on", "who is not on the team anymore", "which tools did we stop using"; `paths::negated_value_frame`, which screens out "not sure" / "why not" / tag questions and the speaker's memory verb) returns that value as a fact line plus the current value for contrast (`recall::negated_value_facts`, reusing the ended-fact path; anchored to named entities or a bare first name that uniquely names one stored person; with no anchored entity it returns nothing (precision first: the global KNN fallback was dropped because no cosine floor separated true entity-less hits from false ones, N11/N12)). The current contrast is injected only against an ended value or a same-subject negated row, so "who does not like jazz" (Bob refuses, Priya likes) keeps the negation filter byte-identical; questions without the frame are unchanged. The typed exclusion channel (`excl`) keeps priority: the frame is off when its property resolved.
- Text-only nickname aliases (H3-08): a nickname stated only in memory text ("Elizabeth Ward, who goes by Liz, ...", "Dmitri Volkov (Dima) ...", "Robert Kessler, known as Bobby, ...", "Jorge Fuentes, called Jo by the team, ..."; `remember::apply_text_nicknames`, `nickname_person_ok`) becomes an alias when a cue phrase (`goes by`, `known as`, `called`, `nicknamed`, `aka`) or a parenthetical names exactly one supplied or stored person entity in the same sentence (re-norming the folded prefix span, so "Fuentes" matches `norm_name`), never for a place/org or any other non-person type, and never when the nickname is already another entity's name or alias - counting one token of a name ("Liz" vs "Liz Zhang", via `name_tokens`) as a collision, which is reported in `hints` instead of added. Heuristic (text-only) writes drop the nickname span's own duplicate entity so `entity <nick>` finds the person card.
- The embedder sets `RAYON_NUM_THREADS` to candle's thread count at model load when unset (gemm and rayon pools must agree; 2x faster).
- Env: `NEOCORTEX_VEC=f32|int8` (vector mode of a new database only), `NEOCORTEX_VEC_PREFILTER=bit` (create and backfill `memories_bits` on open so writes keep it in sync; unset = off), `NEOCORTEX_EMBEDDER=hash` (tests only; a DB records its embedder and refuses another), `NEOCORTEX_DB` (default `~/.neocortex/neocortex.db`), `NEOCORTEX_MODEL_DIR` (default `~/.neocortex/models/UltraBERT-Embed-150M`), `NEOCORTEX_EMBED_DTYPE` (`f32` = `model.safetensors`, `q8` = `model.q8_0.gguf`, `q4k` = `model.q4_k.gguf`; unset = f32 when the safetensors exists, else q8; see the embedder dtype contract), `NEOCORTEX_TZ` (`+HH:MM`, default system local offset), `NEOCORTEX_RERANK_MODEL` (default `~/.neocortex/models/ms-marco-MiniLM-L-6-v2`, optional), `NEOCORTEX_RERANK` (`<N>` / `off`, overrides `Config::rerank_top`), `NEOCORTEX_MAX_TOKENS` (default 1024), `NEOCORTEX_EXTRACTOR` (unset = off; `rules` = `src/extract_model.rs` relation/date tier, used only when a memory has no agent-supplied entities or relations), `NEOCORTEX_DUMP_HOPS=<file>` (appends one JSON line per candidate hop the semantic beam scores: features, evidence memory ids; training data only), `NEOCORTEX_WRITE_TIMING=<file>` (`src/wtiming.rs`: appends one TSV `item` line per stored memory - id, total ms and the 11 stage ms - and one `chunk` line per batch chunk - prepare/embed/write/savepoint ms; off by default, one thread-local check when unset).

## Layout

- `src/db.rs` + `src/schema.sql` - connection, extensions, schema. The vec0 tables are created by `db::create_vec_tables` (not schema.sql) so their element type follows the vector mode. The schema version lives in the `schema_meta` table (v4), never in `PRAGMA user_version`: graphqlite owns that pragma (it stamps 1 and its cypher executor refuses any other value). Migrations are an explicit ladder in `Db::init` (v4 owns every pre-f2 predicate shape: the committed baseline stamps v3 with a three-column `predicates` table); the seeded predicate ontology (23 rows: `predicates.display/group_id/inverse_of/symmetric/seeded`) is reconciled on every v4 open by `Db::seed_predicates(adopt = false)` (Fix-up 2): the current rows and aliases are read once with plain SELECTs, the pending work is collected, and only then is one transaction opened - a complete ontology takes no write transaction at all, so an open never needs the write lock (Fix-up 3: a presence probe is not enough, the `cause` family made an old database look complete, and a `BEGIN IMMEDIATE` on every open made `stats`/`recall`/`validate` fail with "database is locked" while another process wrote, and fail outright on a read-only file). Missing seeded predicates and aliases are inserted, a seeded row's `group_id`/`inverse_of` (and an empty `display`) are repaired; a seed whose canonical arrives in the same pass links to the new rows. The v4-open write is best-effort: SQLITE_BUSY/LOCKED or a read-only file skips it with one stderr line and the next writable open repairs the seeds (a migration's seed step keeps its error, and every other migration is untouched). A canonical or alias already owned by an agent-created (non-seeded) row is never taken over - the user row wins and that seed is skipped whole. Seeded `exclusive` is not agent-settable; a v4 open only corrects it for `mentored by`. The v3 -> v4 migration passes `adopt = true`: pre-v4 rows predate the `seeded` marker, so the seed takes them in and re-applies its display/exclusivity/symmetric policy. H2-14 added the `mentor` (display `mentors`, group `mentor`, inverse `mentored by`) / `mentored by` (non-exclusive — a mentee can have several mentors, unlike `report to`; inverse `mentor`) pair and the `reporting to` / `accountable to` / `is accountable to` aliases of `report to`, which the read-side asked-predicate channel also uses. `memory_links` (E4a), `memory_access` (E5) and the index `idx_rel_subj` on `relations(subj, predicate_id)` (serves the write-path exclusivity lookups and recall's current-values count) are additive and ensured by `Db::ensure_additive_tables` on every v4 open; the schema version stays v4. `rekey_symbol_names` (run on every v4 open, best-effort like the seed reconcile) re-keys entities whose stored `norm` predates TOOL-NAMES (name holds `#`/`+`) or EX-06b (name holds an all-caps abbreviation plural such as "DBs", `GLOB *[A-Z][A-Z]s*`) (norm, name alias, `name_tokens`); it never merges, and `stale_symbol_keys` rows it could not move (new key taken) are reported by `validate` with the holder's id and `run: neocortex merge e<holder> e<stale>`, the command that actually fixes it (EX-06b).
- `memories_bits` (lane nc-binvec) is a derived vec0 table behind the sign-bit prefilter: created and backfilled on demand by `db::ensure_bits`, never by the schema ladder, and dropped without consequence (the next `bit` recall rebuilds it). A stale table (written by a binary without it) is reconciled on the first bit use of each connection, not on every open or recall (see the `db::ensure_bits` contract under `Config.vec_prefilter`).
- `src/embed.rs`, `src/ultrabert.rs` - Embedder trait, UltraBERT forward pass, HashEmbedder (tests), dtype selection (`load_dtype`, `weights_file`, `identity`) and the offline conversion (`quantize_dir` -> `ultrabert::quantize_model`, CLI `neocortex quantize-model <f32 dir> <out dir> [--dtype q8|q4k]`). Weights are read tensor by tensor with plain file reads straight into their final buffer (`SafetensorsFile`; q/k/v and gate/up are read back to back into one fused buffer): peak RSS is one copy of the weights (615 MiB f32; the old mmap + `Tensor::from_slice` + `Tensor::cat` path peaked at 1,190 MiB), the page cache is not charged. candle tensors own their storage (`CpuStorage` is a `Vec`), so nothing can be built zero-copy from an mmap. The quantized model is a GGUF with Q8_0 (or Q4_K) linear weights stored fused (`layers.N.qkv.weight`, `layers.N.gate_up.weight`), a Q8_0 embedding table and f32 norms. Quantized layers are dequantized to f32 in 256-row slabs (`quant_matmul`, L2-resident) and multiplied by the same runtime-dispatched gemm as f32 (AVX2 copy of the dequant loop chosen by `is_x86_feature_detected!`, baseline loop elsewhere): activations stay f32, so q8 error is weight rounding only. candle's own `QMatMul` is not used: its SIMD kernels are chosen at compile time (`target_feature = "avx2"`/`"neon"`), the default x86-64 build falls to scalar code and measured 14 s per recall instead of 0.25 s. No bf16/f16 weights: f16 gemm measured 1.6x slower than f32 and f16 -> f32 conversion 1.2x slower than gemm itself. Cold CLI recall is dominated by reading the weights plus the tokenizer JSON parse (~30 MiB, ~155 ms).
- Embedder dtype contract: the DB-recorded embedder name (`embed::identity`) is the model, not the dtype. f32 and q8 share `ultrabert-150m` because their vectors are interchangeable (measured: cosine q8 vs f32 over 927 eval texts min 0.99836 / mean 0.99959; a DB ingested with f32 queried with q8 scores the same retrieval); a dtype joins that identity only while its parity holds (>= 0.995 mean, >= 0.99 min on `tests/embed_quant.rs`). `q4k` (mean cosine 0.953, min 0.929) fails that bar and has its own name `ultrabert-150m-q4k`, so a DB refuses the other dtype. Default stays f32 (full accuracy, fastest warm path); q8 is the choice for machines under ~1 GB of free RAM. Never ship a build with `-C target-cpu=native` or a required AVX2/AVX-512/FMA flag: SIMD is runtime-dispatched or portable.
- `src/text.rs` - normalisation (`norm_name` and `exact_name_tokens` fold the plural of an all-caps abbreviation onto its singular: "DBs" = "DB", "APIs" = "API", EX-06b), singularise, Jaro-Winkler, trigrams, FTS query building, predicate keys, content hash. `lemma_verb` folds the passive/irregular `led` onto `lead` (`used`/`managed` already strip to their base). Greek accents fold (tonos/dialytika, ς→σ, ё→е); `translit_norm` builds the ER-07 comparison key (Cyrillic→Latin, ю deliberately as "u", German ue/oe/ae digraphs, Slavic endings ky→ki/ow→ov); `name_blocker` is the ER-07 hard-blocker list. `expand_symbols` spells out the symbol suffix of a 1-3 character alphanumeric name before folding ("C#" -> "c sharp", "C++" -> "c plus plus", "A+" -> "plus" after the leading determiner), so `norm_name`/`exact_name_tokens` keep tools that differ only by a stripped symbol (`#`/`+`) on separate entities (TOOL-NAMES); `fold` and the content hash are unchanged, and `.`/`&`/`-` names ("Node.js", "AT&T", "Objective-C") keep their existing keys. `norm_name` also folds version tokens (`text::is_version_token`, `canon_versions`): a `v`/`V` before digits and leading zeros per component are dropped, so "Postgres 16", "Postgres v16" and "Postgres 016" share one name key (VERSIONS-V1); the leading version word of "v2 API" stays part of that name, so it is not "API".
- `src/temporal.rs` - civil dates, instant/window parsing, query windows, history intent, plan/recurrence/ordering/duration cues (`future_event_intent` keeps a matching planned row visible to "when does X start" questions) and calendar duration formatting. `text_dates` is the write-path reader: `remember` stores a date written in the content as `valid_from` (and `valid_to` for a written range) when the caller gave none, reported in `when_inferred`. Supported single dates: `yesterday`/`last night`, `this morning`/`this afternoon`, `last <weekday>` (the most recent such weekday strictly before today), `N days|weeks|months ago` (digits or words to twenty, N = 1 included: `1 day ago`, `one week ago`; the exact day, not the start of its week or month), `last week|month|year` (start of the period), and any absolute date with a four-digit year. Written ranges: `from A to B`, `A to B`, `A - B`, `between A and B` (both ends) and `until B` (end only, start keeps the day's rule). A written last day is inclusive, so "Sep 7 to Sep 9" stores `[09-07, 09-10)` and a duration of 3 days; month/year ends already cover their period. A single month-day form without a year takes the most recent occurrence not in the future (`most_recent_day`); a written range is read in the clock's year, so a yearless range whose start is still ahead ("December 24 to January 2" written in October) dates nothing instead of becoming last year's interval, and a plan cue still resolves through `future_window`. Precision first: vague phrases (`a while back`, `recently`, `last spring`), two unrelated dates, a range that would end before it starts, a declined range phrase itself (bare four-digit pairs are periods only with a cue - `in`/`during`/`since`/`throughout`, `from`, `between` - or a period noun, so page numbers, serials and sample ids date nothing; any weekday pair, bare or with `from`, with or without a recurrence cue, is a weekly schedule rather than one finished interval; a yearless range still ahead of the clock), a partitive `the last week|month|year of X`, a compound number (`twenty-one days ago`), and a cut date token (`to 2026-10` in `to 2026-10-10`) all date nothing; a declined range is blanked before the single-date scan, so an independent date in the same sentence still dates the memory ("We migrated on 2026-07-06; the archive holds 1990 - 2000 data" keeps 07-06). Caller `valid_from`/`valid_to` always win and suppress text inference entirely. A query window is a filter as well as a ranking boost (H2-10, `recall::dated_outside`) only when the question scopes itself to it with a preposition ("in August 2026", "during 2025", "on 2026-08-01"); a month that modifies a noun, with or without a year ("the December conference", "the December 2026 conference"), dates the subject and stays a boost. A memory that states its own interval (`valid_to`, or `valid_from` != `created_at`) and misses the window is dropped; an event without a stored end takes the end its text states ("from X to Y", read back by `recall::stated_end`), and one that states none belongs to the window holding its start; any other open row is still true and overlaps later windows, and a row dated only by its ingest time stays. `as_of` queries keep the old behaviour (no window filter); a window that leaves nothing in view reports `window_empty`.
- `src/extract.rs` - heuristic entity candidates, n-grams for alias lookup. S-03: Unicode-aware capitalisation (`is_acronym`, single capitals, `is_foreign_title_case`) keeps cased non-Latin scripts (Latin diacritics, Greek, Cyrillic, Armenian); caseless scripts (CJK, Arabic) are a documented limit. Calendar/clock/year/duration/ordinal/relative-time spans are rejected (`is_date_like_name`). B5: `CONNECTORS` (`do, da, dos, das, de, del, della, di, du, van, von, der, la, le, of`) stay inside a proper-noun span; a possessive ("Nova's") ends a multi-word span and is stripped from its name ("Universidade Nova", the head after it is a separate span), so "Rua do Instituto Bacteriológico" and "Universidade da Beira Interior" are one entity each and a generic head is never emitted alone; `is_hyphen_tail` keeps a hyphen-glued compound ("cryo-ET", "C-Class") from starting a span ("ET of Lon" is not a name). EX-03 (nc-ex03): two capitalised words before a `SPAN_NOUNS` plural keep the known head and drop the compound unless the compound is already stored or recurs capitalised elsewhere in the same text ("Cypher Memory nodes" with stored Cypher -> "Cypher"; "Cypher Memory ... Cypher Memory" -> "Cypher Memory"). EX-05 (nc-ex03): a sentence-initial single word is kept when `known` (a stored alias) or when it has other name evidence (acronym, inner cap/digit, foreign title case, or recurs capitalised not at sentence start); an unknown sentence-initial word is still kept before a verb cue ("Paris is the capital ..."), as before nc-ex03 (round 2 restored it); "Release Notes:" stays out because opener plurals ("notes") never extend a span. EX-07: a `/`-joined number pair directly after a proper span head yields both version siblings ("Postgres 14/16" -> "Postgres 14" and "Postgres 16"); a pair with no head ("3/4 of", "10/12") or after a common noun ("Meeting 10/12") is not split.
- `src/extract_model.rs` - optional deterministic relation/date tier (off by default). `causal_cue` is the conservative single-cue "A because B" extractor used by E4b. Scored by `examples/extract_eval.rs` on `eval/extract/gold.json` (128 memories; `cargo run --release --example extract_eval -- [gold] [predictions.json] [name]`). Reference predictions and runner scripts: `eval/extract/preds/`, `eval/extract/reference/`. Comparison and candle port plan: `docs/research/extraction.md`.
- `src/graph.rs` - CSR + ACL push personalized PageRank, deterministic Leiden community detection (seeded XorShift visit order, refinement with connected-component splits, aggregation carrying collapsed self-loop weight) and Newman modularity. `src/rank.rs` - RRF, MMR, cosine, packing, and `retention` (E5 score).
- `src/remember.rs`, `src/resolve.rs`, `src/kg.rs` - write pipeline, entity/predicate resolution, and rebuildable graph projection. `remember` and `remember_batch` share `prepare` + `write_prepared`; a batch chunk of <= 256 inputs is one embed call and one transaction with a SAVEPOINT per item. `write_prepared` also writes E4a temporal links. Its near-duplicate check and `related` block share one bounded candidate set (`remember::neighbour_candidates`): the newest 128 FTS hits on the memory's longest content tokens, the newest 256 mentions of each mentioned entity and the newest 512 memories, capped at 1024, scored by point-read cosine (`knn_among`) - never a `memories_vec` KNN scan, so the write cost follows the input, not the corpus. A near duplicate must therefore share a whole word (>= 4 chars), an entity or recency with the stored memory; the old full-vector scan is gone. The temporal-link window is an `idx_memories_valid` range scan with an EXISTS probe on the `mentions` primary key (no memory scan, no GROUP BY). graphqlite edge projection (`kg::project_mention/similar/name_part/relation`) is one `MERGE` statement per edge: the old two-`MATCH` + `MERGE` form planned a cartesian product and cost O(edges) per call on a grown graph. Before each edge, an endpoint whose node is missing or carries no `name` is projected from its relational row (`ensure_memory_node`/`ensure_entity_node`, one Cypher existence probe ~10 us): a bare-id `MERGE` on an unprojected endpoint used to leave a node with only `id`, which no label query can name.  Entities are unique on `(norm, type, homonym)` (types lower-cased); homonym pools resolve by card cosine + memory-context cosine; inverse writes are stored in the canonical predicate direction, symmetric ones once with `src < dst`; negation (`polarity=0`) ends the same `(src, dst, group)` positive interval; a relation whose ends resolve to the same entity is not stored (the reply names each dropped one in `hints`) and a name-like predicate (`nickname`, `alias(es)`, `aka`, `a k a`, `also known as`, `known as`, `goes by`) records its target as an alias instead (`resolve::add_alias`, origin `agent`); exclusivity and conflicts key on the predicate group (`relations.subj`, `predicates.group_id`). The exclusive slot (hunt3 H3-01/03/07, H3-02): the key is the subject, except one-owner predicates (`remember::object_keyed`: canonical `lead`, `own`) which key on the target ("Lars leads portal" ends Sasha's leadership of portal, "Sam leads A" + "Sam leads B" both stay live) and only when the object is a unique one (`remember::unique_object`: a named entity, or a definite "the X" - "Bo owns the repo" ends "Ann owns the repo", "Blake owns a laptop" never ends "Alex owns a laptop", H3-07 follow-up). A seeded exclusive predicate ends every other live value of its key; an agent-declared (unseeded) exclusive `use` (tools, dependencies: multi-valued per subject) ends a value only when the write text names that value as replaced (`remember::names_as_replaced`: "from X", "replaced X", "instead of X", "X was removed/dropped/retired/replaced/deprecated"), so "Atlas uses ESLint" never ends "Atlas uses npm"; other agent-declared exclusive predicates keep the supersede rule ("hosts the club at Café" ends "hosted the club at Biblioteca"). A dated write that finds an ingest-stamped live fact (`starts_at_ingest`: its evidence memory was undated, valid_from = created_at) retires that fact (`expired_at`) instead of becoming history up to the stamp - but only when it asserts the present: an open-ended write whose clause carries no past-tense cue (`remember::says_past`), or one that names the old value as replaced. A closed interval or a historical sentence ("Ann lived in Rome in 2019", "Lars led the portal from 2023 to 2024") is history and backfills instead, never retiring the current fact (H3-02b). The REL-19 exclusive-ending block queries the key side and the value side (the non-key endpoint, so inverted predicates like "reports to" stored as "manages" end correctly) and asks `resolve::near_name`: Below ends the old fact, Merge skips silently, Near/Blocked/Unsure skip and push a `Conflict{relation_id, fact, valid_from}`; relation phrase vectors use `pred_alias = 0.80` with head/tail guards; stale `predicates_vec` is wiped by the v4 migration. B5: `insert_entity` writes the entity's `name_tokens` and calls `link_name_parts`, which finds entities whose exact token set (`text::exact_name_tokens`, unsingularised) strictly contains or is contained in the new name (one indexed token probe, candidate cap 200); the contained side must be a place by type (`PLACE_TYPES`), the container a place or org (`ORG_TYPES`; org inside org never links), no person on either side, and it writes one `name_part` row; `enrich` re-runs it when a later mention fills in an untyped entity's type; the `CONTAINS` edge is projected by `kg::project_name_parts` after `project_entity_from_db`, because the write path links a new entity before its node exists; `merge_entities` moves the merged entity's links and tokens to the survivor like `similar` edges. ER-08: the ER-07 name-layer `Merge` reaches the write path only through `resolve::near_corroborated` - transliteration-key-equal spellings, or a shared person/org neighbour named in the same write that a stored memory of the candidate also mentions; otherwise the mention becomes a new entity reported `ambiguous` with the candidate.
